Do NOT delete or reseed any database data.

Preserve all currently working Workout Builder behaviour.

============================================================
FIX 1 — TRANSACTIONAL REORDER
============================================================

The following reorder operations currently execute multiple UPDATE statements without a database transaction:

- PATCH /plans/:id/days/reorder
- PATCH /plans/:id/days/:dayId/exercises/reorder

Wrap each complete reorder operation in a database transaction.

Requirements:

- The temporary-order phase and final-order phase must use the same transaction.
- If any update fails, all changes must roll back.
- No negative temporary order values may remain in the database.
- Final order values must be normalized to:
  - 1, 2, 3, ...
- Reject duplicate IDs in the request.
- Reject IDs that do not belong to the selected plan or day.
- Verify that all expected records were updated.
- Preserve the existing frontend request format.

After implementation, simulate a failed reorder inside the transaction and prove that the original order remains unchanged.

============================================================
FIX 2 — ASSIGNED CLIENT IN PLAN SUMMARY
============================================================

The Plan Summary Card must display the assigned client.

Use the existing client relationship.

Extend the existing getPlanFull response with the minimum client information required for display, preferably:

- clientId
- clientName

Do not duplicate the complete client record inside the plan.

Display in the Polish UI:

Przypisany klient: <client name>

If the client record is unavailable, display a safe fallback:

Przypisany klient: Nie znaleziono klienta

Update the existing handwritten planApi.ts types consistently.

Do not migrate these routes to OpenAPI during this task.

============================================================
FIX 3 — COMPLETE ACTIVATION VALIDATION
============================================================

Before changing a plan status from Draft to Active, validate the complete plan structure.

Activation must be blocked when required information is missing.

Validate at minimum:

Plan:
- Plan name exists
- Assigned client exists
- At least one training day exists

Every training day:
- Day name exists
- At least one exercise exists

Every exercise entry:
- Referenced Exercise Library exercise exists
- Working sets is a positive integer
- A valid repetition prescription exists
- RIR is between 0 and 5 when provided
- RPE is between 1 and 10 when provided
- Rest time is not negative
- Exercise has required muscle assignments for volume calculation

Repetition validation:

- exact: exact repetition value is required
- range: minimum and maximum are required, minimum must not exceed maximum
- time: duration is required and positive
- distance: distance is required and positive
- open: open instruction is required

Load fields may remain optional unless the selected load type requires a value.

When activation is blocked, return structured validation data, not only one combined message.

Recommended response structure:

{
  "error": "PLAN_ACTIVATION_VALIDATION_FAILED",
  "message": "Nie można aktywować niekompletnego planu.",
  "missingFields": [
    {
      "scope": "plan | day | exercise",
      "dayId": null,
      "exerciseEntryId": null,
      "field": "workingSets",
      "label": "Serie robocze",
      "message": "Ćwiczenie musi mieć co najmniej 1 serię roboczą."
    }
  ]
}

The Plan Editor must display the exact missing items in Polish.

Do not silently activate an invalid plan.

Do not make Draft plans require complete prescriptions. Drafts may remain incomplete.
