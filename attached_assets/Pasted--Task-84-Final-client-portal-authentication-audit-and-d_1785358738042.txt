## Task #84 — Final client-portal authentication audit and deployment readiness check

### Objective

Perform a focused audit of the newly secured client portal authentication before ending today's work.

Do not add new product features.

The goal is to confirm that the Clerk-based client authentication, database migration, frontend requests, and production configuration are internally consistent and ready for the next onboarding task.

---

## Scope

Audit the following areas:

1. `requireClientAuth`
2. `clients.clerk_user_id`
3. `/client-portal/plan`

5. Client portal Clerk integration
6. API request credentials

## Authentication audit

Verify that:

* every protected client-portal plan and session route uses `requireClientAuth`,
* no protected route authorizes access using caller-provided `clientId`,
* no protected route authorizes access using caller-provided email,
* `req.client.id` always comes from the authenticated Clerk identity,
* foreign resources return `404`,
* unauthenticated requests return `401`,
* nested data is loaded only after ownership has been confirmed.

Search the entire API project for:

```text
req.query.clientId
req.body.clientId
req.query.email
req.body.email
/client-portal/plan?email
```

Report every remaining occurrence and classify it as:

* safe,
* unrelated,
* legacy,
* security risk.

Do not blindly remove fields used in legitimate trainer workflows.

---

## Migration audit

Verify that:

```text
0006_add_client_clerk_user_id.sql
```

is:

* present in the migration directory,
* ordered correctly after previous migrations,
* valid for the project's database,
* consistent with the Drizzle schema,
* not duplicated by another migration,
* safe when run once.

Confirm that the database schema and migration both define:

```text
clerk_user_id TEXT UNIQUE
```

with nullable behavior.

Do not create another migration unless the current one is genuinely invalid.

## Frontend Clerk audit

Verify that the client landing application:

* is wrapped in `ClerkProvider`,
* uses the correct publishable key configuration,
* supports sign-in and sign-up,
* waits for Clerk loading state before requesting protected data,
* sends authenticated API requests correctly,
* does not store client identity in `sessionStorage`,
* does not require email or clientId to fetch plans or sessions,
* does not expose email in copied portal URLs.

Check for accidental request loops where the plan endpoint is repeatedly called before authentication finishes.
