# TASK — Workout Plan Draft Generator
# PHASE 1: Generator Input and Configuration Wizard

Implement Phase 1 of the Workout Plan Draft Generator.

This phase creates the trainer-facing input and configuration wizard.

It must collect, validate and present all data required by later generator phases.

Do NOT generate a workout plan yet.
Do NOT select exercises.
Do NOT allocate weekly volume.
Do NOT calculate sets.
Do NOT generate repetitions, RIR, tempo or rest periods.
Do NOT generate warm-ups.
Do NOT implement AI.
Do NOT activate any plan automatically.

Use the approved specification:

docs/workout-plan-draft-generator-spec.md

============================================================
CORE PRODUCT PRINCIPLE
============================================================

The application will eventually generate:

Szkic planu treningowego

The trainer must always remain in control.

Phase 1 must provide a fast and clear configuration experience that:

- pre-fills values from the Training Interview,
- clearly shows missing information,
- allows trainer overrides,
- separates basic and advanced options,
- does not hide where information came from.

The wizard must be usable by a beginner trainer without removing advanced control.

============================================================
APPROVED PRODUCT DECISIONS
============================================================

Implement the following approved decisions.

1. TRAINING SPLIT STORAGE

Add an optional canonical field to workout plans:

splitType

Supported stored values:

- full_body
- full_body_ab
- upper_lower
- upper_lower_full_body
- push_pull_legs
- push_pull_lower_full_body
- specialization
- custom

User-facing Polish labels:

- Full Body
- Full Body A/B
- Góra / Dół
- Góra / Dół / Full Body
- Push / Pull / Legs
- Push / Pull / Dół / Full Body
- Plan specjalizacyjny
- Własny podział

Do not store translated labels as canonical values.

2. BLOCK DURATION

Add:

blockDurationWeeks

Rules:

- integer,
- minimum 4,
- maximum 12,
- default 6,
- trainer editable.

User-facing label:

Długość bloku treningowego

Helper text:

Najczęściej 4–8 tygodni. Wartość można później zmienić.

3. EQUIPMENT NORMALIZATION

Create one centralized equipment-normalization module.

Do not create a new equipment database table.

Use the existing canonical Exercise Library equipment values.

The module may map safe aliases to existing canonical values.

Examples:

- hantle → Hantle
- hantel → Hantle
- sztanga → Sztanga
- wyciąg → Wyciąg
- maszyny → Maszyna
- masa własna → Masa własnego ciała

Do not modify Exercise Library records during this phase.

4. FUTURE DEFAULTS — DOCUMENT ONLY

Record the following approved future defaults in the implementation documentation, but do not apply generation logic yet:

Weekly-volume starting position:

- Brak aktywności fizycznej → lower boundary of the approved range
- Początkujący → approximately 25% inside the approved range
- Średniozaawansowany → middle of the approved range
- Zaawansowany → middle of the range unless trainer priorities justify more

Future adjustments:

- priority muscle: increase within the approved range
- poor recovery: move toward the lower boundary
- high stress or physical work: move toward the lower boundary
- good recovery and sufficient time: may move upward
- never automatically exceed the approved range

Tempo:

- default UI uses a simple Polish description,
- numeric tempo is shown in advanced settings,
- suggested general text:
  “Kontrolowane opuszczanie, płynne podniesienie”.

Do not implement these generation rules in Phase 1.

STEP 1 — DATABASE AND MIGRATION
============================================================

Add non-destructive fields to workout_plans:

- split_type
- block_duration_weeks

Recommended types:

- split_type: nullable text with application-level canonical validation
- block_duration_weeks: integer, nullable or default 6 according to the existing plan-creation architecture

Create a committed, non-destructive migration.

Do not rely only on drizzle push.

Migration requirements:

- preserve all existing plans,
- preserve all existing plan days,
- preserve exercise references,
- preserve clients,
- preserve surveys,
- preserve volume guidelines,
- preserve volume targets,
- do not recreate tables,
- do not reset IDs.

Existing plans should remain valid with:

- splitType = null
- blockDurationWeeks = 6 or null resolved to 6 in the application

Choose the option that best matches the current project conventions and document it.

============================================================
STEP 3 — INPUT PREPARATION SERVICE
============================================================

Create a deterministic backend service such as:

planDraftInputService.ts

Responsibilities:

1. Load the selected client.
2. Load the client's latest Training Interview.
3. Resolve the exact experience level.
4. Load available training days.
5. Load session duration.
6. Load location and equipment.
7. Load activity, work, sleep and stress data.
8. Load priorities.
9. Load preferred exercises.
10. Load avoided exercises and reasons.
11. Normalize equipment values.
12. Return source information for every field.
13. Return structured warnings for missing data.

Do not generate a plan.

Do not select exercises.

Do not calculate weekly volume.

Avoid N+1 queries.

============================================================
STEP 4 — REQUIRED DATA VALIDATION
============================================================

Experience level is required.

Valid values:

- Brak aktywności fizycznej
- Początkujący
- Średniozaawansowany
- Zaawansowany

Missing value:

MISSING_EXPERIENCE_LEVEL

Invalid value:

INVALID_EXPERIENCE_LEVEL

Do not map missing or invalid values to:

- Brak aktywności fizycznej
- Początkujący
- any other level.

Draft generation will eventually be blocked until this is resolved.

Phase 1 should clearly display the problem and allow an explicit trainer override where appropriate.

Other useful warning codes:

- MISSING_TRAINING_GOAL
- MISSING_AVAILABLE_DAYS
- MISSING_SESSION_DURATION
- MISSING_TRAINING_LOCATION
- MISSING_EQUIPMENT
- MISSING_RECOVERY_DATA
- INCOMPLETE_CLIENT_PROFILE

Only critical missing data should block proceeding.

============================================================
STEP 5 — API
============================================================

Add a preparation endpoint consistent with the existing API architecture.

Recommended example:

GET /api/clients/:clientId/plan-draft-input

Response should include:

- client summary,
- latest interview values,
- resolved input values,
- source of each value,
- missing-data warnings,
- default configuration,
- available trainer overrides,
- allowed split types,
- allowed block-duration range.

Do not expose:

- trainer-only private notes unless explicitly required,
- raw security tokens,
- unrelated client data,
- other clients' information.

Optionally add a validation endpoint if it matches the current architecture:

POST /api/plans/draft-input/validate

This endpoint validates configuration only.

It must not generate or save a workout plan.
