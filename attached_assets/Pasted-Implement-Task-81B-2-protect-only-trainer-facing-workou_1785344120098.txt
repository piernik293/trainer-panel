## Goal

An authenticated trainer may access, create, edit, generate, activate, or delete plans only for clients they own.

Rules:

- unauthenticated private request → 401,
- authenticated request for another trainer’s resource → 404,
- ownership must be derived from the database,
- never trust trainerId from request body, query params, headers, or URL,
- when both clientId and planId are present, the plan must belong to that exact client,
- public survey routes and the client-facing portal must remain unchanged.

## 1. Plan routes

Inventory and protect only trainer-facing routes responsible for:

- listing plans for a client,
- creating or saving a plan,
- reading a plan by planId,
- updating a plan,
- changing plan status,
- activating a plan,
- deleting a plan,
- adding, editing, reordering, or deleting plan days,
- adding, editing, reordering, or deleting exercises inside a plan,
- copying or duplicating plans if such routes exist.

For routes containing only planId, derive ownership through:

plan → client → trainer

For routes containing clientId and planId, require:

plan.id = planId
AND plan.clientId = clientId
AND client.trainerId = authenticatedTrainer.id

Do not check ownership only through an unrelated clientId.

## 2. Plan-generation routes

Protect trainer-facing routes responsible for:

- plan-draft input,
- plan-draft validation when client data is involved,
- generate-day,
- balance-week,
- record-generation,
- exercise recommendations,
- volume preview,
- analysis preview,
- other generator endpoints reading a client survey or client history.

Every route referencing a client must verify that the authenticated trainer owns that exact client before generator logic runs.

If a request contains planId:

- verify the plan belongs to the authenticated trainer,
- verify it belongs to the supplied clientId when both IDs exist.

Do not modify generator filtering, exercise choice, volume rules, warnings, or plan structure.

## 3. Nested-resource binding

Verify that IDs cannot be mixed between resources.

Examples that must return 404:

- Trainer A owns Client A and Client C.
- Plan C belongs to Client C.
- Trainer A requests Plan C through Client A’s nested URL.

Also verify:

- a plan day belongs to the supplied plan,
- a plan exercise belongs to the supplied day or plan,
- an exercise cannot be edited through another owned plan’s URL.

## 4. Query enforcement

Where practical:

- enforce trainer ownership in the database condition,
- use owner-scoped joins or subqueries,
- return 404 for foreign or mismatched resources,
- do not load unrestricted plan data and rely on frontend checks.
