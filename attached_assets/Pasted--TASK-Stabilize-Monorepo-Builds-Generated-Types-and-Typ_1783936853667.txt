# TASK — Stabilize Monorepo Builds, Generated Types and TypeScript Checks

This is a stabilization task.

Do NOT add new product features.
Do NOT redesign any UI.
Do NOT modify business logic unless required to fix an actual type inconsistency.
Do NOT change the existing behaviour of the application.

The application currently works at runtime, but TypeScript checks fail because internal workspace package `dist` outputs and generated API types are stale.

The known affected packages are:

- @workspace/db
- @workspace/api-zod
- @workspace/api-client-react

The known additional type gap is that exercise API responses include computed fields:

- isComplete
- missingFields

but these fields are not currently represented in the OpenAPI Exercise schema.

============================================================
OBJECTIVE
============================================================

Make the monorepo fully type-safe and reproducible.

Expected final result:

- Internal workspace packages are rebuilt from current source
- Generated OpenAPI/Zod/client types match the actual API
- `isComplete` and `missingFields` are included in the official Exercise response type
- API server TypeScript check passes
- Trainer app TypeScript check passes
- Existing runtime behaviour remains unchanged
- Existing database data remains untouched

============================================================
STEP 0 — SAFETY CHECK
============================================================

Before modifying anything:

1. Inspect the current git status.
2. Create a git commit or restore point for the current working implementation.
3. Record the existing build and typecheck errors.
4. Do not reset, delete or overwrite existing feature work.
5. Do not delete the database or reseed existing user data.

Do not proceed with destructive operations.

============================================================
STEP 3 — FIX THE OPENAPI EXERCISE RESPONSE TYPE
============================================================

The API returns computed completeness fields on exercise responses:

- isComplete
- missingFields

Add these fields to the official OpenAPI Exercise schema.

Use appropriate types:

- `isComplete`: boolean
- `missingFields`: array of strings

These are response fields computed by the server.

Do not store them as database columns.

Do not duplicate the completeness logic.

The existing dynamic completeness calculation must remain the single source of truth.

Ensure these fields are present in every API response type where an Exercise object is returned.
