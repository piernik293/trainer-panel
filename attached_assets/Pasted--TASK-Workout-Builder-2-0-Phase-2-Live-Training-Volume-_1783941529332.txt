# TASK — Workout Builder 2.0, Phase 2: Live Training Volume Calculation

This task extends the existing Workout Builder 2.0 Phase 1.

This is PHASE 2 only.

The goal is to add live session and weekly muscle-volume calculations to the Plan Editor by reusing the existing Volume Calculator, exercise muscle assignments, muscle coefficients and approved volume guidelines.

Do NOT implement plan balance analysis, estimated workout duration, advanced training methods, automatic plan generation or AI during this task.

============================================================
IMPORTANT SAFETY RULES
============================================================

Preserve all existing functionality from Workout Builder Phase 1.

Do NOT:

- Replace or rewrite the existing Volume Calculator
- Duplicate volume-calculation business logic in the frontend
- Change muscle coefficients
- Change exercise muscle assignments
- Change approved volume-guideline values
- Change the 44 existing volume-guideline rows
- Change the four experience levels
- Change Training Interview logic
- Change Exercise Recommendation Engine scoring
- Delete or reseed database data
- Remove existing plans
- Add automatic exercise selection
- Automatically modify a trainer’s plan
- Introduce new activation-blocking rules
- Implement AI

The existing backend Volume Calculator must remain the single source of truth.

If existing activation logic already blocks a specific absolute-volume violation, preserve that behaviour exactly. Do not create additional blocking rules during this task.

Before modifying anything:

1. Inspect the existing Volume Calculator.
2. Inspect the current volume-guideline schema and live database rows.
3. Inspect the 11 existing volume targets.
4. Inspect exercise muscle assignments and coefficients.
5. Inspect Workout Builder Phase 1 plan, day and exercise structures.
6. Inspect current plan activation volume validation.
7. Report any architectural conflict before making a destructive change.

============================================================
OBJECTIVE
============================================================

While the trainer creates or edits a workout plan, the application should calculate and display:

- Effective sets added by every exercise
- Volume for every muscle in each training day
- Total weekly volume for every muscle
- Current volume compared with the client’s approved guideline values
- Session minimum
- Session maximum
- Weekly preferred ceiling
- Weekly absolute ceiling
- Exact exercise contributions to each muscle
- Clear warnings about missing data or exceeded guidelines

Calculations must update without requiring the trainer to activate the plan.

The trainer must always remain in control.

The system should calculate, explain and warn — never automatically remove exercises, reduce sets or change the plan.

============================================================
SOURCE OF VOLUME GUIDELINES
============================================================

Use only the existing approved volume-guideline records stored in the database.

The application currently supports four independent experience levels:

1. Brak aktywności fizycznej
2. Początkujący
3. Średniozaawansowany
4. Zaawansowany

The existing database contains 11 muscle targets for each level, for a total of 44 guideline rows.

Every guideline contains the existing fields:

- sessionMin
- sessionMax
- weeklyPreferredCeiling
- weeklyAbsoluteCeiling

Do not hardcode these values in the frontend.

Do not recreate the numeric tables in another service.

Do not change or reinterpret the existing approved values.

The client’s experience level must be taken from the existing Training Interview and mapped through the existing guideline-level mapping.

============================================================
VOLUME CALCULATION RULES
============================================================

Effective volume must use the existing muscle assignments and coefficients.

For each exercise entry:

effective sets for one muscle =
workingSets × muscle coefficient

Example:

Exercise:
- Working sets: 4

Muscle assignments:
- Latissimus dorsi: coefficient 1.00
- Biceps: coefficient 0.50
- Trapezius: coefficient 0.25

Result:
- Latissimus dorsi: 4.00 effective sets
- Biceps: 2.00 effective sets
- Trapezius: 1.00 effective set

Requirements:

- Use all valid muscle assignments connected to the exercise.
- Include primary and secondary assignments.
- Use the stored coefficient exactly.
- Do not infer volume only from exercises.mainMuscleGroup.
- Do not treat every secondary muscle as a full set.
- Do not round individual contributions before summing.
- Preserve fractional effective sets.
- Round only for display, preferably to a maximum of two decimal places.
- Calculations must be deterministic.
- The same saved plan must always return the same volume result.

============================================================
SESSION VOLUME
============================================================

Calculate volume separately for every training day.

For each day show:

- Muscle name
- Effective sets in this session
- Session minimum
- Session maximum
- Session status
- Exercises contributing to the result

Session statuses:

- Below minimum
- Within recommended session range
- Above session maximum
- Guideline unavailable

Recommended Polish UI labels:

- Poniżej zalecanej objętości
- W zalecanym zakresie
- Powyżej zalecanej objętości na jednostkę
- Brak wytycznych

Do not treat being below session minimum as a critical error.

It should be an informational signal, especially for draft plans.

============================================================
WEEKLY VOLUME
============================================================

Calculate weekly volume by summing all training days in the plan.

Unless the current architecture already stores a separate weekly frequency for each day, count every workout day exactly once per week.

Do not invent a frequency field during this task.

For each muscle show:

- Current weekly effective sets
- Weekly preferred ceiling
- Weekly absolute ceiling
- Remaining volume before preferred ceiling
- Remaining volume before absolute ceiling
- Weekly status

Weekly statuses:

1. Below or equal to preferred ceiling
2. Above preferred ceiling but below or equal to absolute ceiling
3. Above absolute ceiling
4. Guideline unavailable

Recommended Polish labels:

- W bezpiecznym zakresie
- Przekroczono preferowany limit
- Przekroczono absolutny limit
- Brak wytycznych

Do not introduce a weekly minimum if it does not exist in the approved database structure.

============================================================
LIVE PREVIEW ARCHITECTURE
============================================================

The trainer must see updated volume while editing a draft, including before saving it.

Do not duplicate the calculation formula in React.

Create or extend a backend preview mechanism that accepts the current unsaved plan structure and calculates volume using the existing backend Volume Calculator logic.

Preferred architecture:

- A preview endpoint accepts the current plan draft snapshot.
- It does not save or mutate the plan.
- It validates the provided exercise IDs and working sets.
- It loads muscle assignments and coefficients from the database.
- It loads the client’s experience level and approved guidelines.
- It returns a calculated preview.
- It uses the same calculation functions as saved-plan volume calculations.

The frontend should call the preview endpoint with a reasonable debounce.

Recommended debounce:

- approximately 300–600 ms after the last relevant edit

Do not call the endpoint on every keypress without debounce.

Relevant changes that should refresh the preview:

- Adding an exercise
- Removing an exercise
- Duplicating an exercise
- Moving an exercise between days
- Changing working sets
- Reordering days or exercises when the displayed breakdown depends on order
- Changing the assigned client
- Changing an exercise reference

Changes such as trainer notes should not trigger unnecessary volume recalculation.

============================================================
MISSING DATA AND WARNINGS
============================================================

The calculator must handle incomplete data safely.

Return structured warnings for:

- Exercise without muscle assignments
- Exercise with invalid coefficient
- Missing exercise record
- Missing client survey
- Missing experience level
- Missing guideline level
- Missing guideline for a muscle target
- Invalid working sets
- Exercise entry without an exercise ID

Recommended warning structure:

{
  "code": "EXERCISE_WITHOUT_MUSCLE_ASSIGNMENTS",
  "scope": "exercise",
  "dayId": 2,
  "exerciseEntryId": 15,
  "exerciseId": 5,
  "message": "Ćwiczenie nie ma przypisanych mięśni i nie zostało uwzględnione w objętości."
}

Requirements:

- Do not crash the editor because one exercise is incomplete.
- Calculate all valid contributions.
- Clearly list what was excluded.
- Do not silently treat missing assignments as coefficient 1.00.
- Do not silently assign a guideline level.
- Do not silently map “Brak aktywności fizycznej” to “Początkujący”.

Inactive exercises already present in existing plans should remain readable and should still contribute to volume when valid muscle assignments exist.

Show an inactive-exercise warning, but do not erase its historical contribution.

============================================================
SAVED PLAN CALCULATION
============================================================

The same calculation result should be available for a saved plan.

Requirements:

- Reloading the page produces the same result.
- A saved plan can request its calculated volume without sending the entire draft snapshot.
- Draft preview and saved-plan calculation use the same core calculation functions.
- Avoid separate formulas for preview and persisted plans.

Recommended approach:

- A pure internal calculation function receives normalized plan days and exercise entries.
- Saved-plan endpoint loads the plan from the database and calls it.
- Draft-preview endpoint validates and normalizes the request and calls the same function.

============================================================
PERFORMANCE
============================================================

Avoid N+1 database queries.

Load in batches where possible:

- Exercise records
- Muscle assignments
- Muscle targets
- Volume guidelines

The calculation should remain responsive for plans containing:

- Up to 7 training days
- Up to 20 exercise entries per day
- Multiple muscle assignments per exercise

Frontend preview requests should:

- Be debounced
- Cancel or ignore stale responses
- Show a loading state
- Keep the last valid result visible during recalculation
- Not display an older response after a newer edit

============================================================
VALIDATION
============================================================

Validate preview input on the backend.

At minimum:

- Client ID exists
- Day structure is valid
- Exercise ID exists when provided
- workingSets is a positive integer when included in calculation
- coefficient is a valid non-negative number
- Duplicate temporary frontend IDs do not corrupt the response
- Invalid entries produce structured warnings or validation errors

Draft plans may remain incomplete.

Do not require complete exercise prescriptions such as load, RIR, RPE or tempo for volume calculation.

Only exercise identity, working sets and valid muscle assignments are required to calculate effective sets.

============================================================
BACKWARD COMPATIBILITY
============================================================

Existing plans must continue to load.

Plans created before Phase 2 may contain:

- Missing working sets
- Missing exercise assignments
- Inactive exercises
- Null prescription fields
- Old optional fields

Handle them safely.

Do not change historical plan data automatically.

Do not write calculated volume totals permanently into plan rows unless the current architecture already does this and has a verified invalidation mechanism.

Prefer calculating from current source data rather than storing stale totals.
