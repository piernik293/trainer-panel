# TASK — Workout Builder 2.0, Phase 1: Stable Core Plan Editor

This task extends the existing Plan Editor.

This is PHASE 1 only.

The goal is to create a stable, professional workout-plan editor that allows the trainer to manually build and edit training plans.

Do NOT implement live volume calculations, automatic workout generation, AI planning, advanced plan analysis or progressive overload during this task.

Preserve all existing application behaviour.

============================================================
IMPORTANT SAFETY RULES
============================================================

Do NOT:

- Remove existing Plan Editor functionality
- Modify the Training Interview logic
- Modify the Volume Calculator
- Modify muscle coefficients
- Modify the Exercise Recommendation Engine
- Modify Exercise Library metadata
- Modify client records
- Delete existing workout plans
- Reset or reseed the database
- Redesign unrelated parts of the application
- Implement AI
- Automatically generate complete workout plans

If an existing structure already supports part of this task, extend it instead of creating a competing implementation.

Before changing code:

1. Inspect the existing plan-related database schema.
2. Inspect the current Plan Editor UI.
3. Inspect the existing API routes and generated client hooks.
4. Inspect how plans are currently assigned to clients.
5. Inspect whether draft plans and saved plans already use separate states.
6. Report any conflict between this specification and the existing architecture before making a destructive change.

============================================================
OBJECTIVE
============================================================

Create a professional manual Workout Builder where the trainer can:

- Create a workout plan
- Assign it to a selected client
- Add multiple training days
- Add exercises to every day
- Configure exercise prescriptions
- Reorder exercises and days
- Duplicate exercises and days
- Save unfinished work safely
- Edit previously saved plans
- Preserve all entered data after page refresh

The trainer must remain in full control.

============================================================
SECTION 1 — PLAN INFORMATION
============================================================

Every workout plan should support:

- Plan name
- Client
- Goal
- Description
- Start date
- Optional end date
- Status:
  - Draft
  - Active
  - Archived
- Optional trainer notes

Use existing client and goal data where available.

Do not duplicate client records or Training Interview fields.

The plan should remain editable while it is a draft.

Activating or archiving a plan must not delete it.

============================================================
SECTION 2 — TRAINING DAYS
============================================================

Allow the trainer to add multiple training days.

Every day should support:

- Day name
- Optional subtitle
- Optional description
- Optional estimated duration placeholder
- Trainer notes

Examples:

- Dzień A — Góra ciała
- Dzień B — Dół ciała
- Trening 1
- Full Body A

Required actions:

- Add day
- Rename day
- Reorder days
- Duplicate day
- Delete day
- Confirm before deleting a day that contains exercises

Deleting one day must not affect other days.

============================================================
SECTION 3 — ADDING EXERCISES
============================================================

Exercises must be selected from the existing Exercise Library.

Reuse the current Exercise Picker and Recommendation Engine where possible.

Do not create a second independent exercise database or picker.

The trainer should be able to:

- Search exercises
- Use existing recommendations
- Open exercise details
- Add an exercise to the selected training day
- Add the same exercise to different training days
- Add the same exercise more than once when intentionally needed

When adding an exercise, preserve the existing warnings and recommendation information.

Warnings must not prevent manual selection.

Examples:

- Client wants to avoid this exercise
- Exercise is above the client’s experience level
- Missing equipment
- Incomplete metadata
- High joint stress

============================================================
SECTION 4 — EXERCISE PRESCRIPTION
============================================================

Every exercise added to a workout day should support:

- Number of working sets
- Repetition prescription
- Load prescription
- RIR
- RPE
- Tempo
- Rest time
- Trainer notes
- Client-facing instructions

============================================================
SETS
============================================================

Allow the trainer to choose a practical number of working sets.

The value should be a positive integer.

Do not implement volume limits in this phase.

============================================================
REPETITIONS
============================================================

Support:

- Exact repetitions
  Example: 10

- Repetition range
  Example: 8–12

- Time-based prescription
  Example: 30 seconds

- Distance-based prescription
  Example: 20 metres

- Open instruction
  Example: AMRAP

Use a clear data structure rather than storing every option as an unvalidated free-text field.

Do not remove the possibility of a trainer note for unusual prescriptions.

============================================================
LOAD PRESCRIPTION
============================================================

Support optional load instructions such as:

- Fixed weight
- Percentage of 1RM
- Bodyweight
- Bodyweight plus additional load
- Assisted bodyweight
- Trainer-defined instruction

Do not implement automatic load progression yet.

============================================================
RIR AND RPE
============================================================

Support optional:

- RIR from 0 to 5
- RPE from 1 to 10

The trainer may use:

- RIR only
- RPE only
- Neither

Avoid forcing both fields simultaneously.

Do not automatically convert RIR into RPE.

============================================================
TEMPO
============================================================

Support optional four-part tempo notation.

Example:

3-1-1-0

Display a short helper explaining the notation.

Do not reject an exercise when tempo is empty.

============================================================
REST TIME
============================================================

Support rest time in seconds.

The UI may display friendly values such as:

- 60 s
- 90 s
- 2 min
- 3 min

Store the value consistently.

============================================================
NOTES
============================================================

Support two separate note types:

- Private trainer note
- Client-facing instruction

Private trainer notes must not be shown in the future Client Portal unless explicitly changed later.

============================================================
SECTION 5 — EXERCISE ACTIONS
============================================================

Every exercise entry should support:

- Edit
- Reorder
- Move to another day
- Duplicate
- Delete

Confirm before deleting an exercise when unsaved edits could be lost.

Duplicating an exercise should copy:

- Exercise
- Sets
- Repetitions
- Load prescription
- RIR
- RPE
- Tempo
- Rest time
- Notes

The trainer can edit the duplicate independently.

============================================================
SECTION 6 — DRAG AND DROP
============================================================

Add drag-and-drop support where it can be implemented reliably.

Support:

- Reordering exercises within one day
- Moving exercises between days
- Reordering training days

Requirements:

- Keyboard-accessible alternative controls must remain available
- Dragging must not accidentally delete an item
- Order must persist after saving and refreshing
- Mobile and narrow-screen layouts must remain usable

If the existing project already uses a drag-and-drop library, reuse it.

Do not introduce multiple drag-and-drop libraries.

============================================================
SECTION 7 — DRAFT AND SAVE BEHAVIOUR
============================================================

The editor must protect the trainer from losing work.

Implement:

- Explicit Save action
- Unsaved changes indicator
- Warning before leaving with unsaved changes
- Reliable persistence after saving
- Loading state
- Save success state
- Save failure state

Optional autosave may be added only if the current architecture already supports it safely.

Do not rely only on frontend state.

Saved plans must persist in the database.

A failed save must not show a false success message.

============================================================
SECTION 8 — EDITING EXISTING PLANS
============================================================

The trainer must be able to reopen an existing plan and see:

- Correct plan information
- Correct day order
- Correct exercise order
- All exercise prescription fields
- Trainer notes
- Client-facing notes
- Current status

Editing and saving an existing plan must update the correct plan.

Do not create duplicate plans accidentally during an update.

============================================================
SECTION 9 — PLAN SUMMARY
============================================================

Add a simple summary that displays:

- Number of training days
- Total number of exercise entries
- Total number of working sets entered
- Plan status
- Assigned client
- Last saved time

This is a structural summary only.

Do NOT yet show:

- Muscle volume analysis
- Weekly volume limits
- Push/Pull balance
- Movement-pattern balance
- Fatigue score
- Recovery score
- AI assessment

Those belong to later phases.

============================================================
SECTION 10 — USER EXPERIENCE
============================================================

Keep the current professional trainer-focused UI style.

The editor should have clear hierarchy:

1. Plan information
2. Training days
3. Exercises
4. Exercise prescription
5. Plan summary
6. Save controls

Use Polish user-facing labels consistent with the rest of the application.

Recommended terminology:

- Kreator planu treningowego
- Dzień treningowy
- Dodaj ćwiczenie
- Serie robocze
- Powtórzenia
- Obciążenie
- RIR
- RPE
- Tempo
- Przerwa
- Notatka trenera
- Instrukcja dla klienta
- Zapisano
- Niezapisane zmiany
- Wersja robocza
- Aktywny
- Zarchiwizowany

Do not introduce English labels into the Polish UI.

============================================================
DATA AND API REQUIREMENTS
============================================================

Inspect the existing schema before adding anything.

Reuse existing plan tables where possible.

The data model must preserve:

- Plan identity
- Client assignment
- Day order
- Exercise order
- Exercise Library reference
- Prescription fields
- Notes
- Status
- Created timestamp
- Updated timestamp

Use foreign keys to the existing Exercise Library and client records where appropriate.

Do not copy the full exercise definition into every plan entry.

A plan exercise should reference the Exercise Library exercise by ID.

Historical plan entries must remain readable even if an exercise later becomes inactive.

Use transactions for multi-part plan saves when supported by the existing database layer.

Do not delete existing records during schema updates.

============================================================
VALIDATION
============================================================

Validate on both frontend and backend where appropriate.

Examples:

- Plan name is required
- Client is required before activation
- Day name is required
- Exercise ID must exist
- Sets must be a positive integer
- RIR must be between 0 and 5
- RPE must be between 1 and 10
- Rest time cannot be negative
- Exercise order must remain valid
- Day order must remain valid

Draft plans may contain incomplete prescriptions.

An incomplete draft must not be silently activated.

When activating an incomplete plan, show exactly what is missing.

============================================================
BACKWARD COMPATIBILITY
============================================================

Existing workout plans must remain accessible.

If old plans do not contain the new optional fields:

- Load them safely
- Use empty defaults
- Do not crash
- Do not overwrite them until the trainer saves changes

Do not remove or rename existing API routes without providing compatibility.

Regenerate OpenAPI and API client types using the existing project workflow when endpoints or schemas change.

Rebuild affected workspace packages after generation.

============================================================
OUT OF SCOPE
============================================================

Do NOT implement in this task:

- Live muscle-volume calculation
- Session volume limits
- Weekly volume limits
- Preferred or absolute ceiling warnings
- Push/Pull/Squat/Hinge analysis
- Movement-pattern balance
- Estimated training duration logic
- Supersets
- Compound sets
- Drop sets
- Rest-pause
- Cluster sets
- Myo-reps
- Automatic exercise selection
- Automatic plan generation
- AI planning
- Progressive overload
- Load recommendations
- Injury adaptation
- Client workout execution
- Training history
- Client Portal
- Chat
- Notifications

Prepare the architecture so these can be added later without rebuilding the core editor.

============================================================
EXPECTED RESULT
============================================================

The application should have a stable and professional manual workout builder.

The trainer should be able to create, edit, organise and save complete workout plans without losing data.

The implementation must provide a reliable foundation for later phases:

- Phase 2: Live volume calculations
- Phase 3: Plan analysis and warnings
- Phase 4: Advanced training methods
- Future Client Portal
- Future automatic plan generation
- Future AI assistance

Do not implement those later phases now.
