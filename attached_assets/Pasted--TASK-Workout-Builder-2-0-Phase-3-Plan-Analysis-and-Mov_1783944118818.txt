# TASK — Workout Builder 2.0, Phase 3: Plan Analysis and Movement Balance

This task extends the existing Workout Builder 2.0 after completion of:

- Phase 1 — Stable Core Plan Editor
- Phase 2 — Live Training Volume Calculation

This is PHASE 3 only.

The goal is to add live structural analysis of the workout plan, including movement-pattern coverage, Push/Pull balance, Squat/Hinge balance, exercise-type distribution and bilateral/unilateral balance.

The system must analyse and explain the plan.

It must never automatically modify the trainer’s decisions.

============================================================
IMPORTANT SAFETY RULES
============================================================

Preserve all existing functionality.

Do NOT:

- Rewrite or replace the Volume Calculator
- Modify approved volume-guideline values
- Modify muscle coefficients
- Modify exercise muscle assignments
- Modify Training Interview logic
- Modify Exercise Recommendation Engine scoring
- Modify Exercise Library relationships
- Remove or replace Workout Builder functionality
- Automatically add exercises
- Automatically remove exercises
- Automatically reorder days or exercises
- Automatically change sets or repetitions
- Automatically replace exercises
- Introduce new activation-blocking rules
- Implement automatic workout generation
- Implement AI
- Delete or reseed database data
- Redesign unrelated parts of the application

This phase should remain advisory.

Warnings and analysis must not prevent the trainer from saving or editing a draft plan.

If existing activation rules block specific issues, preserve them exactly. Do not add new blocking rules without explicit approval.

Before implementation:

1. Inspect the current Workout Builder.
2. Inspect the Phase 2 preview architecture.
3. Inspect existing exercise metadata.
4. Inspect all existing movement-pattern and Exercise Intelligence fields.
5. Inspect the current Plan Editor state structure.
6. Inspect handwritten planApi.ts types.
7. Inspect how unsaved plan snapshots are currently sent to backend preview endpoints.
8. Report any architectural conflict before making a destructive change.

============================================================
ANALYSIS UNITS
============================================================

Calculate two separate measures:

1. Exercise-entry count
2. Working-set count

Example:

Plan contains:

- Bench Press — 4 sets
- Dumbbell Press — 3 sets
- Cable Fly — 3 sets
- Pull-Up — 4 sets

Push:
- 3 exercise entries
- 10 working sets

Pull:
- 1 exercise entry
- 4 working sets

Use working-set count as the main balance signal.

Show exercise-entry count as additional context.

Do not use effective muscle-volume coefficients to calculate movement-pattern balance.

One working set of an exercise contributes one set to its movement category.

If one exercise legitimately belongs to multiple categories, use one primary movement category for balance calculations and additional tags only for informational display.

Do not double-count one set in multiple primary categories.

============================================================
BALANCE RULE ARCHITECTURE
============================================================

Do not scatter arbitrary thresholds throughout UI code.

Create one centralized analysis configuration.

Example structure:

{
  pushPull: {
    warningRatio: 1.5,
    strongWarningRatio: 2.0,
    minimumCombinedSets: 6
  },
  squatHinge: {
    warningRatio: 1.75,
    strongWarningRatio: 2.5,
    minimumCombinedSets: 4
  },
  categoryDominance: {
    warningPercentage: 45,
    strongWarningPercentage: 60
  },
  unilateral: {
    informationalMinimumDays: 3
  }
}

These are heuristic coaching signals, not medical rules.

Keep thresholds transparent, documented and easy to adjust later.

Do not present them as universal scientific limits.

Do not store these thresholds in the database during this phase.

============================================================
PUSH / PULL ANALYSIS
============================================================

Calculate:

pushPullRatio = pushWorkingSets / pullWorkingSets

Handle zero safely.

Possible statuses:

- Balanced
- Push dominant
- Strongly push dominant
- Pull dominant
- Strongly pull dominant
- Insufficient data

Recommended Polish labels:

- Zrównoważony Push/Pull
- Przewaga ruchów wypychających
- Duża przewaga ruchów wypychających
- Przewaga ruchów przyciągających
- Duża przewaga ruchów przyciągających
- Za mało danych do oceny

Do not issue a balance warning when the combined Push and Pull volume is too small for a useful comparison.

Show the exact values that produced the status.

Example:

Push: 14 serii
Pull: 8 serii
Stosunek: 1,75 : 1

squatHingeRatio = squatWorkingSets / hingeWorkingSets

- Hinge dominant
- Strongly hinge dominant
- Insufficient data

Recommended Polish labels:

- Duża przewaga wzorca przysiadu
- Przewaga wzorca zawiasowego

============================================================
WEEKLY DISTRIBUTION
============================================================

Analyse how movement patterns are distributed between training days.

For every category show:

- Total weekly sets
- Number of days containing the category
- Highest number of sets in one day
- Percentage concentrated in one day

Example:

Pull:
- 12 sets weekly
- Present on 2 days
- 8 sets concentrated in Day A
- 66.7% concentrated in one session

Potential informational warnings:

- All weekly sets for one major movement category occur in a single day
- A movement category is repeated heavily on consecutive listed days
- One day contains an unusually high percentage of the entire plan’s working sets

Do not assume calendar dates or actual recovery time between days.

The editor only knows plan order, not the exact weekly schedule.

Phrase warnings carefully.

Example:

"Cała tygodniowa objętość ruchów przyciągających znajduje się w jednym dniu planu."

Do not claim that recovery will definitely be insufficient.

============================================================

- Tempo

- Rest time

Avoid firing separate duplicate requests for the same unchanged snapshot.
