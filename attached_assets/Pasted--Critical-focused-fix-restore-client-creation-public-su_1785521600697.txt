# 3. Automatically create a survey invitation after client creation

After successfully creating the client:

1. Create an invitation assigned to:
   - the authenticated trainer,
   - the newly created client.

2. Generate a cryptographically secure token.

3. Store only the secure representation required by the existing invitation system.
   Do not store or log plaintext tokens unnecessarily.

4. Build the correct public survey URL.

5. If an email address was provided, attempt to send the link.

Reuse the existing survey-invitation system rather than introducing another incompatible token table.

## Invitation requirements

The invitation must:

- be single-use,
- have an expiration date,
- support revocation,
- belong to one trainer and one client,
- not expose internal IDs as authentication,
- not use the email address itself as proof of identity.

If an active invitation already exists, follow the existing safe behavior for regeneration or revocation.

# 5. Failure handling

Client creation must not be rolled back only because email delivery failed.

## Case A — client, invitation and email succeed

Show:

`Klient został dodany, a link do wywiadu wysłano na adres: {email}`

Actions:

- `Przejdź do klienta`
- `Skopiuj link`

## Case B — client and invitation succeed, email fails

Keep both records.

Show:

`Klient został dodany, ale nie udało się wysłać wiadomości e-mail.`

Actions:

- `Wyślij ponownie`
- `Skopiuj link`
- `Przejdź do klienta`

Do not claim delivery success.

## Case C — no email supplied

Create the client and invitation.

Show:

`Klient został dodany. Skopiuj link do wywiadu i wyślij go klientowi samodzielnie.`

Actions:

- `Skopiuj link`
- `Przejdź do klienta`

## Case D — invitation creation fails

Do not hide the failure.

If the client was already created, show:

`Klient został dodany, ale nie udało się utworzyć linku do wywiadu.`

Provide:

- `Spróbuj ponownie`
- `Przejdź do klienta`
