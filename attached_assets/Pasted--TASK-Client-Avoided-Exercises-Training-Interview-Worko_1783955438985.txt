# TASK — Client Avoided Exercises
# Training Interview + Workout Builder Warning

Implement a professional feature allowing a client to specify exercises they want to avoid.

The feature must connect:

Training Interview
→ client profile
→ Exercise Library
→ Workout Builder
→ plan analysis and warnings

This is a trainer-support feature.

It must inform the trainer, but it must never automatically block an exercise from being added to a plan.

Do NOT implement AI during this task.

============================================================
CORE PRODUCT RULE
============================================================

The application should help the trainer make decisions, not make decisions instead of the trainer.

When a trainer selects an exercise that the client wants to avoid, display:

Klient chce unikać tego ćwiczenia

Also display the client's reason when available.

The trainer must still be able to:

- add the exercise,
- keep it in the plan,
- replace it,
- remove it,
- ignore the warning intentionally.

Do not block saving or activating the plan only because an avoided exercise is present.

============================================================
IMPORTANT SAFETY RULES
============================================================

Preserve all existing functionality.

Do NOT:

- change the existing Training Interview conditional logic,
- rename “Wywiad treningowy” to “Ankieta”,
- modify the four experience levels,
- modify volume calculations,
- modify the 44 volume-guideline rows,
- modify the 11 volume targets,
- modify Phase 2 formulas,
- modify Phase 3 formulas,
- delete exercises,
- recreate exercise IDs,
- reset or reseed the database,
- automatically remove exercises from plans,
- automatically replace exercises,
- let AI decide which exercise the client meant,
- create medical diagnoses,
- block trainer manual control.

============================================================
STEP 1 — AUDIT THE CURRENT DATA FLOW
============================================================

Before implementation, inspect:

- Training Interview schema,
- survey database tables,
- survey API schemas,
- client profile API,
- client profile frontend types,
- Training Interview form state,
- Exercise Library API,
- Workout Builder exercise picker,
- plan validation,
- plan warnings,
- existing database migrations.

Determine:

- where client exercise preferences are currently stored,
- whether there is already an “exercises to avoid” text field,
- whether exercise IDs are already supported,
- whether survey responses are versioned,
- how existing survey records should be migrated safely.

Do not remove existing client answers.

If an old free-text field exists, preserve its content and migrate or display it safely.

============================================================
STEP 2 — DATA MODEL
============================================================

The main connection must use Exercise Library IDs.

Do not store only exercise names.

Preferred model:

avoidedExercises: [
  {
    exerciseId: number,
    reason: string | null
  }
]

Also support an unmatched free-text entry:

avoidedExerciseOtherText: string | null
avoidedExerciseOtherReason: string | null

If the existing project architecture does not support nested survey objects cleanly, use an equivalent normalized structure, for example:

- avoidedExerciseIds: number[]
- avoidedExerciseReasons: Record<string, string>
- avoidedExerciseOtherText: string | null
- avoidedExerciseOtherReason: string | null

Do not use one shared reason for multiple selected exercises when separate reasons can be supported safely.

Requirements:

- one client may select multiple exercises,
- each selected exercise may have an optional reason,
- the same exercise cannot be selected twice,
- exercise IDs must reference existing Exercise Library records,
- selected values must survive survey editing,
- selected values must appear in the client profile,
- removed or inactive exercises must not corrupt existing survey data.

Use a safe database migration.

Do not destroy or overwrite existing survey answers.

============================================================
STEP 3 — TRAINING INTERVIEW UI
============================================================

Add or improve the section:

Ćwiczenia, których chcesz unikać

Helper text:

Wyszukaj ćwiczenia, których nie chcesz wykonywać. Możesz również podać powód, np. dyskomfort, brak pewności technicznej lub zwykłą niechęć.

Create a searchable multi-select connected to the active Exercise Library.

Client interaction:

1. Client starts typing an exercise name.
2. Application shows matching exercises.
3. Client selects one exercise.
4. Selected exercise appears as a removable item.
5. Client may optionally provide a reason.
6. Client may add more exercises.

Example search:

Input:

podciąg

Suggestions:

- Podciąganie na drążku
- Podciąganie na drążku chwytem neutralnym
- Podciąganie na maszynie wspomagającej

Each suggestion should display useful supporting information where available:

- exercise name,
- main muscle group,
- equipment,
- movement pattern.

Do not show raw database IDs in the UI.

============================================================
SEARCH BEHAVIOUR
============================================================

Exercise search should handle:

- lowercase and uppercase differences,
- Polish diacritics,
- leading and trailing spaces,
- partial names,
- repeated spaces.

Example:

podciaganie

should be able to find:

Podciąganie na drążku

Do not use AI or fuzzy semantic matching during this task.

Use deterministic normalized search.

Limit initial results for performance, for example 10–20 suggestions.

Do not load hundreds of full exercise records unnecessarily when a search endpoint already exists.

============================================================
SELECTED EXERCISE DISPLAY
============================================================

For each selected exercise display:

- exercise name,
- optional reason field,
- remove action.

Reason label:

Dlaczego chcesz unikać tego ćwiczenia? — opcjonalnie

Example reasons:

- Czuję dyskomfort w barku
- Nie lubię tego ćwiczenia
- Nie czuję się pewnie technicznie
- Mam złe doświadczenia z tym ruchem
- Nie mam dostępu do potrzebnego sprzętu

Do not force the client to provide a reason.

Do not treat every reason as a medical contraindication.

============================================================
UNKNOWN EXERCISE OPTION
============================================================

Add an option:

Nie znajduję ćwiczenia / nie znam jego nazwy

After selecting it, show:

Opis ćwiczenia

Helper text:

Opisz, jak wygląda ruch, na jakim sprzęcie jest wykonywany lub z czym Ci się kojarzy.

Example:

Leżę na ławce i wypycham sztangę. Przy tym ruchu czuję dyskomfort w barku.

Also show an optional field:

Dlaczego chcesz go unikać?

Store this answer separately from Exercise Library IDs.

Do not automatically match this text to an exercise.

============================================================
STEP 4 — CLIENT PROFILE
============================================================

Display the saved information in the trainer's client profile.

Recommended section:

Ćwiczenia, których klient chce unikać

For matched Exercise Library records display:

- exercise name,
- reason,
- active/inactive status if relevant,
- link or action to open the exercise details where supported.

For unmatched free text display:

Nieznane ćwiczenie — opis klienta

Then show:

- client's description,
- reason.

If no avoided exercises exist, display:

Klient nie wskazał ćwiczeń, których chce unikać.

Do not hide unmatched text answers.

============================================================
STEP 5 — WORKOUT BUILDER INTEGRATION
============================================================

Connect the feature to the currently selected client.

When the trainer creates or edits a plan for a client:

- load that client's avoided exercise IDs,
- compare them with exercises shown in the picker,
- compare them with exercises already present in the plan.

Display a warning in the exercise picker before selection.

Recommended warning:

Klient chce unikać tego ćwiczenia

When a reason exists:

Powód klienta: Czuję dyskomfort w barku

The warning should be visually noticeable but not look like a system error.

Recommended visual treatment:

- warning icon,
- amber/yellow background or border,
- clear label,
- no red blocking state unless another real safety validation requires it.

Do not use a disabled button.

The trainer must still be able to click:

Dodaj ćwiczenie

============================================================
WARNING AFTER ADDING AN EXERCISE
============================================================

If the trainer adds an avoided exercise, show the warning directly on the exercise card in the plan editor.

Example:

Klient chce unikać tego ćwiczenia

Powód klienta: Nie czuję się pewnie technicznie.

Trainer actions may include:

- Pozostaw w planie
- Zamień ćwiczenie
- Usuń z planu

Do not automatically trigger replacement.

If the trainer leaves the exercise in the plan, keep the warning visible.

============================================================
PLAN-LEVEL WARNING SUMMARY
============================================================

Add a non-blocking warning to the plan validation or analysis summary.

Suggested warning code:

CLIENT_AVOIDS_EXERCISE

Suggested structure:

{
  "code": "CLIENT_AVOIDS_EXERCISE",
  "scope": "exercise",
  "exerciseId": 123,
  "exerciseName": "Podciąganie na drążku",
  "reason": "Nie czuję się pewnie technicznie.",
  "blocking": false
}

The warning should be generated for every avoided exercise present in the plan.

Do not duplicate the same warning multiple times for the same plan-exercise entry unless it appears on separate days and the current warning architecture intentionally works per entry.

============================================================
PLAN ACTIVATION
============================================================

An avoided exercise must not automatically prevent:

- saving a draft,
- updating a plan,
- activating a plan.

Before activation, show a clear summary when avoided exercises are present.

Example:

Plan zawiera ćwiczenia, których klient chce unikać.

- Podciąganie na drążku
  Powód: dyskomfort w łokciu

Trainer confirmation:

Rozumiem i chcę aktywować plan

Use this confirmation only if the existing activation flow supports confirmations cleanly.

Do not create a hard backend validation failure.

============================================================
CLIENT-SPECIFIC LOGIC
============================================================

Warnings must be specific to the selected client.

Example:

Client A avoids Bench Press.
Client B does not avoid Bench Press.

Result:

- Plan for Client A shows a warning.
- Plan for Client B does not show a warning.

Do not store avoidance state globally on the exercise record.

Do not mark the exercise itself as unsafe or unavailable.

============================================================
SURVEY EDITING AND HISTORY
============================================================

When the Training Interview is edited:

- previous selected exercises must load correctly,
- reasons must load correctly,
- unmatched text must load correctly,
- removed selections must be removed from the current response,
- historical survey versions should remain readable if history exists.

If a client later removes an exercise from the avoidance list:

- existing plans should no longer show it as a current client preference warning,
- historical survey versions should still preserve the previous answer where supported.

Do not silently rewrite survey history.

============================================================
INACTIVE OR DELETED EXERCISES
============================================================

Prefer soft deletion or inactive status according to the existing Exercise Library architecture.

If an avoided exercise becomes inactive:

- retain its stored ID,
- display its last known name where available,
- show an “Nieaktywne ćwiczenie” label,
- do not crash the client profile or Workout Builder.

Do not erase client preferences simply because an exercise becomes inactive.

============================================================
API REQUIREMENTS
============================================================

Update the existing API schemas and generated or handwritten types safely.

Validate:

- exercise IDs are numeric,
- IDs exist when saving a new survey,
- duplicate IDs are rejected or normalized,
- reasons are trimmed,
- empty reason strings become null where appropriate,
- free-text fields have reasonable length limits,
- malformed payloads return structured validation errors.

Suggested limits:

- reason: maximum 500 characters,
- unknown exercise description: maximum 1000 characters,
- unknown exercise reason: maximum 500 characters.

Use the project's existing validation library and error format.

============================================================
PERFORMANCE
============================================================

Do not request the entire Exercise Library with full descriptions on every keystroke.

Use:

- existing paginated search,
- debounced search,
- lightweight exercise summaries,
- cached selected records where appropriate.

Avoid N+1 queries when resolving multiple avoided exercise IDs.

Load selected exercises in one query.

============================================================
ACCESSIBILITY AND UX
============================================================

Ensure:

- search works with keyboard,
- suggestions can be selected using Enter,
- focus states are visible,
- selected exercises can be removed accessibly,
- labels are connected to inputs,

- loading, empty and error states are shown.

Nie znaleziono ćwiczenia.
