## Goal

An authenticated trainer may access or modify saved workout plans only when they belong to that trainer’s client.

Rules:

- unauthenticated private request → 401,
- authenticated request for another trainer’s resource → 404,
- ownership must be derived from the database,
- never trust trainerId from request bodies, URL parameters, query parameters, or headers,
- nested resources must belong to the exact parent resource in the URL.

## Protect saved-plan routes

Inventory and protect only routes responsible for:

- listing plans for a client,
- creating and saving a plan for a client,
- reading a plan by planId,
- updating plan information,
- changing plan status,
- activating a plan,
- deleting a plan,
- creating, editing, reordering, and deleting plan days,
- creating, editing, reordering, and deleting exercises stored inside plan days,
- copying or duplicating a saved plan if such a route exists.

## Ownership resolution

For a route containing only planId, derive ownership through:

plan → client → trainer

For a route containing clientId and planId, require:

- plan.id = planId,
- plan.clientId = clientId,
- client.trainerId = authenticated trainer id.

For plan days require:

- day belongs to the exact plan,
- plan belongs to the trainer’s client.

For stored plan exercises require:

- exercise record belongs to the exact day,
- day belongs to the exact plan,
- plan belongs to the trainer’s client.

Do not authorize an operation merely because the trainer owns another client, plan, or day appearing in the URL.

## Database enforcement

Where practical:

- apply trainer ownership inside the database condition,
- use owner-scoped joins or subqueries,
- return 404 for foreign or mismatched resources,
- do not rely on frontend checks,
- do not first load unrestricted sensitive data and check ownership afterward.
