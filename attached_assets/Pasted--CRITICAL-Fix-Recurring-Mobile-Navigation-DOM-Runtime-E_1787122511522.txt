# CRITICAL — Fix Recurring Mobile Navigation / DOM Runtime Errors

I need you to investigate and permanently fix a recurring issue in the application that occurs primarily during mobile navigation and rapid user interaction.

**Do not treat this as a cosmetic UI issue. I need you to find the actual root cause in the code, implement the fix, and verify it.**

---

# 1. CONFIRMED RUNTIME ERRORS

I have captured two real runtime errors on a mobile device.

### Error A — `removeChild`

```text
[plugin:runtime-error-plugin]

Nie udało się wykonać polecenia „removeChild” na węźle „Node”:
Węzeł, który ma zostać usunięty, nie jest elementem podrzędnym tego węzła.
```

Equivalent DOM error:

```text
NotFoundError:
Failed to execute 'removeChild' on 'Node':
The node to be removed is not a child of this node.
```

### Error B — `insertBefore`

```text
[plugin:runtime-error-plugin]

Nie udało się wykonać polecenia „insertBefore” na węźle „Node”:
Węzeł, przed którym ma zostać wstawiony nowy węzeł, nie jest elementem podrzędnym tego węzła.
```

Equivalent DOM error:

```text
NotFoundError:
Failed to execute 'insertBefore' on 'Node':
The node before which the new node is to be inserted
is not a child of this node.
```

These errors are displayed by the Vite runtime error overlay.

**Do NOT solve this by disabling the Vite overlay.**

For example, do NOT use:

```text
server.hmr.overlay = false
```

That would only hide the error instead of fixing it.

# 2. WHEN THE PROBLEM HAPPENS

The errors appear most frequently on mobile when the user:

* presses Back,
* uses the mobile browser Back gesture,
* clicks/taps an element once,
* taps the same element twice quickly,
* taps again while an action is still processing,
* clicks something and immediately presses Back,
* navigates to another screen and immediately goes back,
* enters a screen, leaves it quickly, and enters it again,
* rapidly navigates between screens,
* interacts with a screen immediately after returning to it.

The issue is intermittent, so do not assume that every occurrence has exactly the same trigger.

The important correlation is:

**mobile navigation + rapid interaction + component lifecycle/state changes + DOM runtime error.**

# 3. INVESTIGATE THE ACTUAL ROOT CAUSE

Before changing code, inspect the existing architecture and trace the relevant code paths.

Do not immediately add debounce, delays, try/catch, or button disabling.

Investigate whether the error is caused by:

### React lifecycle / reconciliation

Check:

* component mounting/unmounting,
* conditional rendering,
* React reconciliation,
* unstable or incorrect `key` values,
* components being mounted/unmounted during navigation,
* state updates during unmount,
* effects running after a component has already changed or unmounted.

### `useEffect` and cleanup

Check:

* all relevant `useEffect()` hooks,
* event listeners,
* subscriptions,
* timers,
* intervals,
* observers,
* animation callbacks,
* cleanup functions.

Verify that listeners/subscriptions are not registered multiple times and that cleanup is performed exactly where appropriate.

### Manual DOM manipulation

Search the codebase for:

```text
appendChild
removeChild
insertBefore
remove()
replaceChild
innerHTML
outerHTML
createElement
```

Determine whether application code or a dependency is manually manipulating DOM nodes that React also controls.

### Portals / overlays / modals

Pay particular attention to:

* React portals,
* modals,
* dialogs,
* dropdowns,
* popovers,
* tooltips,
* toast/notification systems,
* overlays,
* elements rendered into `document.body`,
* components using DOM APIs directly.

These are especially important because they can create DOM ownership conflicts during rapid unmount/remount cycles.

### Animations

Check animation libraries and custom animations that may manipulate or remove DOM elements while React is simultaneously updating the same component.

### Routing / browser history

Inspect:

* routing configuration,
* `navigate()`,
* browser history,
* `pushState`,
* `replaceState`,
* `popstate`,
* Back buttons,
* mobile Back gestures,
* navigation triggered after asynchronous operations.

Make sure one Back action cannot accidentally trigger multiple navigation/state transitions.

### Async operations / race conditions

Inspect:

* API requests,
* promises,
* mutations,
* loading states,
* async callbacks,
* navigation after requests,
* state updates after navigation,
* requests resolving after a component has unmounted,
* stale closures,
* operations resolving out of order.

Pay special attention to:

```text
User taps
↓
Action/request starts
↓
User taps again OR presses Back
↓
Component changes/unmounts
↓
Original async operation finishes
↓
Old callback/effect attempts to update UI / navigate / manipulate DOM
↓
DOM is no longer in the expected state
↓
removeChild / insertBefore error
```

This is one of the scenarios that must be investigated, not assumed.
